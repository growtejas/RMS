# Performance baseline - 2026-05-08

This is the canonical "before" measurement for the RMS performance architecture
program. Every later phase ships its own delta against this file. Numbers are
filled in from `perf_request_summary` log lines and Chrome DevTools timings
captured during a 10-minute representative recruiter session (login -> TA list
-> open requisition -> ATS tab -> shortlist).

## How to capture

1. `npm run dev` (web) and `npm run worker:cie-intelligence` (or the worker
   fleet you are exercising) running side by side.
2. Reproduce the recruiter journey. Capture `perf_request_summary` log lines
   for the routes below. Each line now includes:
   - `duration_ms` (route total)
   - `db_query_count` (Drizzle queries observed)
   - `auth_ms_jwt`, `auth_ms_user_db`, `auth_ms_org_db` (where applicable)
   - `auth_path` ("db_full" today; "claims" / "db_cached" after Phase 1)
   - `queue_ms_enqueue` (ranking GET / recompute path)
3. Save the raw log fragment under `docs/perf/raw/baseline-<route>.log`.

## Performance budgets (targets)

These are the post-program targets, not today's numbers:

| Metric                                        | Target              |
|-----------------------------------------------|---------------------|
| TTFB p50 / p95 (warm GET, authenticated)      | 80 ms / 250 ms      |
| TTFB p95 (write/admin)                        | 600 ms              |
| INP p75 (TA detail interactions)              | 200 ms              |
| Hydration / TTI requisition detail (4G)       | 1.5 s               |
| Web pod DB pool saturation                    | < 60% steady        |
| Per-request DB queries (read GET)             | <= 1 + route data   |
| BullMQ enqueue p95                            | 20 ms               |
| Per-request enqueue calls from hot GETs       | 0                   |
| LCP p75                                       | 2.5 s               |
| React commit p95 on tab switch                | 50 ms               |

## Notes / observations

- Capture clusters of "many requests finish at ~12 s together" by exporting
  the network panel HAR; cross reference against `perf_request_summary` to
  attribute the wait to auth_ms_user_db, queue_ms_enqueue, or route DB time.
- If `auth_ms_user_db` p95 is the dominant component of TTFB, Phase 1
  (auth fast path) is the highest-leverage fix.
- If `queue_ms_enqueue` is the dominant component on ranking GET, Phase 4
  (remove enqueue from GET) is the dominant fix.
